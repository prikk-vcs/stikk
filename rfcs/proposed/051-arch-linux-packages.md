# RFC 051 — Arch Linux packages on the AUR

**Status.** **Proposed 2026-10-21** by the architect, on the project owner's direction of the same day: *"As extension on
ArchLinux packaging, I registered the repositories which are expected to be integrated with GitHub Actions CI"* —
`aur.archlinux.org/packages/stikk` and `…/stikk-bin`. **Four questions only the owner can answer** (§ *For the owner*).
Measured on CachyOS (Arch-based, x86_64) with `makepkg` and `namcap` against the published stikk 0.15.0, building
packages and installing nothing: `.git-exclude/reports/051-aur/measure051.txt`, with the two PKGBUILDs measured beside
it.
**Tracks.** RFC 048 (**decision 6 is amended**: the AUR moves from *not now* to *now*, on the owner's word), RFC 039
(the release assets), RFC 011 (the release workflow), `NFR-R03`.
**Touches.** A new `packaging/aur/` (two PKGBUILD templates), `release.yml` (one job after the assets are published), a
new `aur.yml` (the templates built on every change), the install page, `ROADMAP.md`.

## Summary

The owner registered four AUR packages under one account: **`stikk`, `stikk-bin`, `prikk` and `prikk-bin`**, each a
`0.0.0` placeholder today. This RFC designs stikk's two: what each builds from, what it depends on, how a release
updates them without a person, and what must be true before the first one is published. prikk's two are prikk's
(RFC 048's principle: each program installs itself — and packages itself).

## Findings

### F1 — what is registered

`aur.archlinux.org/rpc/v5/info`: `stikk`, `stikk-bin`, `prikk`, `prikk-bin`, maintainer `nabbisen`, each `Version
0.0.0-1`, *"A placeholder package for …"*. stikk's two hold a PKGBUILD whose `package()` echoes *Placeholder* and whose
checksum is `DUMMY-FOR-INITIALIZATION`.

### F2 — both shapes build and lint, measured

- **`stikk-bin`** from the release's **static musl archives** (`x86_64` and `aarch64`): `makepkg` packages
  `/usr/bin/stikk` and the README and CHANGELOG under `/usr/share/doc`. With `options=('!strip' '!debug')` **the
  installed binary is byte-identical to the attested release artifact** (`cd26a1eb…` both), so `gh attestation verify`
  speaks for what pacman installed. `namcap`: three warnings, all explained — `x86_64` named in `source_x86_64` (the
  per-architecture source array requires it), *unstripped* (on purpose, above), and `prikk` *"may not be needed"* (stikk
  runs prikk as a program; namcap only sees linked libraries).
- **`stikk`** from **the crates.io crate** `stikk-<ver>.crate`: it carries its own `Cargo.lock`, so `cargo fetch
  --locked` then `cargo build --frozen --release` reproduce the published dependency set; `check()` runs the crate's 10
  tests. Built in about 11 s here (dependencies cached). `namcap`: use `libgcc` rather than `gcc-libs` (Arch's current
  split), and the same `prikk` note.
- **Why the crate, not a GitHub tag tarball**: a published crate is immutable and its sha256 is in the crates.io index
  (`cksum`, measured equal to the downloaded file), while GitHub's generated archives have changed their bytes before.

### F3 — `prikk` as a dependency

stikk is useless without prikk, and the AUR is a package manager resolving **prikk's own** package — so a dependency is
right, and stikk installs nothing of prikk's itself. But today `prikk` on the AUR is a **0.0.0 placeholder**: an
unversioned `depends=('prikk')` would install it and leave the user with no prikk. **`depends=('prikk>=0.<floor>')`**,
the floor derived from `version.rs` as the installers' is, refuses the placeholder by version. And it makes `stikk`
**uninstallable until prikk's AUR packages are real**: honest, but a reason not to publish stikk's first.
`stikk-bin`'s dependency is satisfied by `prikk-bin` only if prikk-bin declares `provides=('prikk=<ver>')`.

### F4 — what pushing asks for

The AUR accepts pushes over SSH to `aur@aur.archlinux.org:<pkg>.git`, authenticated by **an SSH key on the maintainer's
AUR account**; the account's keys are not scoped per package. A CI job that pushes stikk's two therefore holds a key
that could push **all four**, prikk's included. Each push needs the PKGBUILD **and** a `.SRCINFO` generated by
`makepkg --printsrcinfo`, which needs an Arch environment (the `archlinux:base-devel` container).

## Decisions

1. **Two packages, as registered.** **`stikk`** builds the crates.io crate (F2); **`stikk-bin`** installs the
   release's static musl archive for `x86_64` and `aarch64`, unstripped, `provides=("stikk=$pkgver")`,
   `conflicts=('stikk')`. Both install `/usr/bin/stikk` and the docs, and nothing else.
2. **`depends=('prikk>=0.<floor>')`** in both, the floor filled from `print_version_matrix` like the installers'
   (F3). No upper bound: a newer prikk runs, and stikk says so (`NFR-R03`).
3. **The PKGBUILDs live in this repository as templates** (`packaging/aur/stikk/PKGBUILD.in`,
   `packaging/aur/stikk-bin/PKGBUILD.in`), filled at release time with the version, the floor and the checksums — the
   `-bin` ones from the release's own `.sha256` files, the source one from the crates.io index. **No number is written
   by hand**, as with the installers.
4. **`release.yml` publishes them**, in one job after the assets and the crates are published, in `archlinux:base-devel`:
   fill both templates, **build both with `makepkg` as a non-root user, run `namcap`, refuse on any warning not in a
   short allow-list** (decision 1's three, F2), generate `.SRCINFO`, and push each to its AUR repository. The AUR host
   key is **pinned**, never accepted on first use. **A failed AUR push does not fail the release** — the release is
   already public — it is reported, and a `workflow_dispatch` with a version input re-runs the job alone.
5. **`aur.yml` builds the templates on every change** to `packaging/aur/**`, filled against the latest published
   release, with `makepkg` and `namcap`, and **pushes nothing**. A template is never first tested by a release.
6. **stikk is not published to the AUR before prikk is** (F3). The job exists and is tested from the start; the push
   is enabled by the owner (O3) once prikk's AUR packages install a real prikk.
7. **The install page** gains a short *Arch Linux* section: `stikk-bin` (or `stikk` to build it), installed with
   `makepkg -si` from the AUR repository or an AUR helper, and that it pulls in prikk's own AUR package. It names neither
   helper as required.
8. **RFC 048 decision 6 is amended**: the AUR is a channel now, at the owner's direction; the reasons there for the
   others (winget, Scoop, Snap, Flatpak, …) stand.

## Delivery

**One handoff on acceptance, for 0.16.0 if the owner adds it to the scope** (increment 5; it touches only packaging and
CI, so it can run beside exchange): the two templates, `aur.yml`, the `release.yml` job with the push behind the
owner's switch (O3), the install page's section. **Measured before review**: both templates filled for the published
release build and pass `namcap` within the allow-list in `archlinux:base-devel` on CI; the `.SRCINFO` matches
`makepkg --printsrcinfo`; the push step is exercised against a **dry run** (no push) until O2 and O3 exist.

## What this RFC does not do

- **No prikk packaging**: `prikk` and `prikk-bin` are prikk's.
- **No other package manager**; RFC 048 decision 6's reasons stand for them.
- **No `aarch64` build test**: no Arch Linux ARM runner. The `aarch64` line uses the archive Handoff B of RFC 048
  proved on real ARM hardware; the PKGBUILD's `aarch64` branch is lint-checked only.
